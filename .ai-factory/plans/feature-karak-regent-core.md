# Implementation Plan: Karak: Regent, part 1 of 3 — expansion toggle, Lord Karak rooms, new monsters and spells

Branch: feature/karak-regent-core (created from feature/art-generation @ 602ee9a; the Karak branches are merged to main together)
Created: 2026-10-15

## Original Request
Karak Regent, часть 1 из 3 (правила в .ai-factory/references/karak-regent-rules.md): переключатель «Дополнение Regent» при создании игры (хранится на Game, влияет на колоду тайлов, мешок и список героев), комнаты Лорда Карака — Боевая арена (дуэль героев при первом входе) и Проклятая комната (бросок 1–3 = проклятие), монстры Гигантская летучая мышь (6 HP → Шип тьмы) и Скелет-маг (11 HP → Морозный кулак), заклинания Шип тьмы и Морозный кулак, арты через tools/art. Ветка от feature/art-generation.

Follow-up answers: PHPUnit only (showcase e2e untouched); logging standard; docs yes; the curse model with the expansion is "several cursed heroes at once" (the mummy token stays single and movable, Cursed Room curses are a separate list on Game; a hero is cursed while either applies; a fountain or the Portal lifts both).

## Settings
- Testing: yes (PHPUnit only; `fe/e2e/tests/two-player-game.spec.ts` is NOT changed)
- Logging: standard (message-bus middleware logs the commands/events; no extra log statements; the art tool keeps its INFO per asset)
- Docs: yes (rules.md "Karak: Regent" section, README bullet, RulesView section, tools/art README + STYLE.md, base-theme README)

## Requirements Reconciliation
Authority: `.ai-factory/references/karak-regent-rules.md` (rules digest) > user request and follow-up answers > existing implementation (`Game.php`, `Deck.php`, `Bag.php`, `Field.php`, `Battle.php`, `Movement.php`, `GameTurn.php`, `TurnAction.php`, `Player.php`). Where the digest is silent, the decision below is the contract.

Game shape that constrains the design: the lobby creates one human + one virtual player and the game view has no polling (`gamePollingInterval` is never started); the showcase e2e plays two humans in one browser by switching `currentPlayerId`. A virtual player's whole turn runs server-side in one request (`/game/virtual-player-turn`), so a human can never decide anything inside a virtual player's turn.
